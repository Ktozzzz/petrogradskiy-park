# Демонстрационные сценарии

Пять сценариев показывают работу всех ключевых функций сервиса.
Подсказки для них есть в интерфейсе (раздел «Умный запрос») и в API (`GET /api/scenarios`).

## Сценарий 1. Ближайший объект к координатам (KNN)

**Запрос:** «Какой парк находится ближе всего к координатам 59.9598, 30.3126?»

**Что происходит:** правила/LLM извлекают intent `nearest_distance` и координаты;
backend выполняет KNN-запрос по GiST-индексу `p.centroid <-> точка` и возвращает
объект с расстоянием в метрах и временем пешком.

**В интерфейсе:** раздел «Ближайший», ввод координат -> объект подсвечивается на карте.

**Проверка API:**
```bash
curl "http://127.0.0.1:8000/api/parks/nearest_distance?latitude=59.9598&longitude=30.3126"
```

## Сценарий 2. Сколько идти от ориентира (Location Resolver)

**Запрос:** «Сколько до ближайшего парка от Электровокзала?»

**Что происходит:** Location Resolver ищет «Электровокзал» сначала в собственной БД
`geo_places` (триграммный индекс), при неудаче — во внешнем геокодере; затем
считается расстояние `ST_Distance(geography)` и время пешком (~4,8 км/ч).

**В интерфейсе:** подсказка в разделе «Умный запрос» -> ответ с расстоянием и картой.

**Проверка API:**
```bash
curl -X POST http://127.0.0.1:8000/api/query \
  -H "Content-Type: application/json" \
  -d '{"text": "Сколько до ближайшего парка от Электровокзала?"}'
```

## Сценарий 3. Объекты в радиусе (ST_DWithin)

**Запрос:** «Покажи все скверы в радиусе 1 км от Чкаловского проспекта»

**Что происходит:** intent `radius_search`, категория `square`, радиус 1000 м;
`ST_DWithin` по geography отсекает кандидатов по индексу, точные расстояния
считаются для ответа, объекты нумеруются на карте по удалённости.

**В интерфейсе:** раздел «В радиусе» -> список и нумерованные метки на карте.

**Проверка API:**
```bash
curl "http://127.0.0.1:8000/api/parks/radius?latitude=59.9598&longitude=30.3126&radius_m=1000&category=square"
```

## Сценарий 4. Что внутри объекта (POI + условные знаки)

**Запрос:** «Что интересного внутри Летнего сада?»

**Что происходит:** backend находит объект по названию (`get_park_by_name`), затем
возвращает точки интереса, попавшие внутрь контура (`ST_Covers`), сгруппированные
по типам: памятники, фонтаны, туалеты, места питания.

**В интерфейсе:** карточка объекта + слой условных знаков на карте
(☕ питание, ★ памятники, ◎ аттракционы, ⛹ детские площадки, ⚽ спорт,
⛲ фонтаны, ⚑ смотровые, 🚻 туалеты, ⛴ парковки).

**Проверка API:**
```bash
curl -X POST http://127.0.0.1:8000/api/query \
  -H "Content-Type: application/json" \
  -d '{"text": "Что интересного внутри Летнего сада?"}'
curl "http://127.0.0.1:8000/api/parks/1/poi"
```

## Сценарий 5. Рекомендация по смыслу (гибридный рейтинг)

**Запрос:** «Найди парк с детской площадкой и местом для пикника недалеко от метро»

**Что происходит:** текст превращается в вектор (семантическая часть), кандидаты
ранжируются по формуле `0.50·семантика + 0.30·близость + 0.20·категория`,
веса берутся из конфигурации. Каждый результат сопровождается объяснением:
какие теги совпали, расстояние до точки отсчёта, вклад каждой компоненты.

**В интерфейсе:** раздел «Рекомендации» -> карточки с процентами вклада
(«смысл 81% · близость 74% · категория 80%») и текстовым объяснением.

**Проверка API:**
```bash
curl -X POST http://127.0.0.1:8000/api/recommend \
  -H "Content-Type: application/json" \
  -d '{"query": "детская площадка и место для пикника недалеко от метро",
       "latitude": 59.9563, "longitude": 30.3165, "radius_meters": 3000, "limit": 5}'
```

## Дополнительно: отказ AI

Если Ollama/LLM недоступны, любой из запросов выше выполняется локальными правилами
разбора: ответ содержит `source: "rules"` и предупреждение в `warnings`,
а вся геопространственная часть работает без изменений. Это проверяется просто —
запустите сервис без запущенной AI-модели.
